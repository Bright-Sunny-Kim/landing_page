P0

감사조서/분석 결과 영속화

참고: Step 04 참고: Step 05 참고: Step 06
✅ 완료

기존에 저장되지 않던 working_paper_md(Step 04 산출물)를 audit_working_papers 테이블(회사/연도/버전 + draft→reviewed→approved 상태)에 영속화하는 API·UI 구현을 완료했습니다. FK 정합성을 위해 companies 마스터 테이블(자연키: 사업자등록번호)을 신설하고 audit_working_papers.company_id가 이를 참조합니다.

✅ 구현 및 검증 완료

  • companies/audit_working_papers/audit_working_paper_logs 테이블 설계 (database/audit_working_papers_schema.sql) 및 DB 마이그레이션 실행 완료
  • 조서 저장(POST /master/audit-working-paper/<company>/save) — 마스터가 명시적으로 저장 버튼을 눌러야 새 버전 생성
  • 버전 이력 조회 및 상태전이(draft→reviewed→approved) API + master_detail.html UI 연결
  • 마스터 화면에서 분석→저장(버전 자동 증가)→상태전이 end-to-end 클릭 검증 통과

P1

T/B 파싱 로직 통합 (BS/IS 빌더 · 대차평형 · Delta 비교)

참고: Step 01 참고: Step 04
🔶 부분 구현

Step 01·04가 각자 parse_tb_file을 직접 호출해 T/B를 파싱하고 있어, 하나를 고치면 다른 하나가 깨지는 이중 유지보수 상태입니다. audit_engine.py가 파싱·병합(merge_multiple_tb_dfs)과 변동성 분석(run_variance_analysis)까지는 처리 중입니다.

🔶 남은 작업

  • P0 저장소에 표준화 데이터를 남기고 Step 04가 재파싱 대신 이를 읽도록 통합
  • 표준 재무상태표(BS)/손익계산서(IS) 자동 빌더 + 대차평형 검증
  • 고객 제시 재무제표와의 Delta 비교 알고리즘, Dify 기반 차이 원인 분석 보고서 생성
  • n8n Webhook 트리거 연동 (원래 설계대로, 현재는 Flask 직접 호출)
↓
P2

계정과목 표준매핑 (부분 자동화 + 수동 오버라이드)

참고: Step 01 참고: Step 04
⏸ 미착수

parse_tb_file은 현재 컬럼명 키워드 매칭('계정', '당기' 등)에만 의존하고, 매칭 실패 시 모의 데이터로 Fallback합니다. 회사마다 계정명이 달라 이 상태로는 확장이 어렵습니다.

🔶 남은 작업

  • 계정과목 표준매핑 테이블 신설 (Supabase)
  • 완성형 매핑이 아니라, 매칭 실패 시 마스터가 수동 지정 → 다음부터 자동 반영되는 부분 자동화 구조로 설계
↓
P3

RAG 지식 베이스 유지보수 (상시 트랙, 병행 가능)

참고: Step 02 참고: Step 03
🔶 진행 중 (Step 02 완료 · Step 03 미가동)

Step 02(K-GAAP/GAAS RAG)는 process_local_pdfs.py로 Supabase document_chunks에 적재 완료되어 AI FAQ가 실시간 사용 중입니다. 반면 Step 03(DART RAG)은 dart_audit_reports/dart_report_chunks 스키마와 크롤러 스크립트만 있고 정기 실행이 연결되지 않아 실데이터가 없습니다. 순번상 3번째 단계라서 여기서 진행하는 게 아니라 P0~P2와 병행 가능한 독립 서비스입니다.

🔶 남은 작업

  • DART 크롤러(scripts/dart_crawler.py)를 n8n 또는 cron으로 정기 실행 연결 → 실데이터 적재 개시
↓
P4

감사보고서 초안 생성 라우트 신설

참고: Step 05
⏸ 미착수

P0(영속화) 완료 전에는 조서 결과를 안정적으로 읽어올 방법이 없어 착수 자체가 무의미합니다.

🔶 남은 작업

  • 감사조서(Step 04) + DART 유사문구(Step 03)를 결합해 의견문단/주석 초안을 만드는 /master/audit-report-draft 라우트 신설
↓
P5

교차검증 워크플로 (평가 방법론 정의 우선)

참고: Step 06
⏸ 미착수

"AI가 AI를 검토"하는 로직은 정답 세트(ground truth) 없이는 판단 기준이 없어 무기한 막힐 위험이 가장 큰 항목입니다.

🔶 남은 작업

  • 실제 감사보고서 샘플에 대한 기대 결과를 먼저 정의 (평가 방법론)
  • 두 번째 LLM 패스(Dify reviewer)로 K-GAAS 체크리스트 대조 → 논리적 오류 검증
  • 마스터 승인 시 확정 처리하는 워크플로 구축
